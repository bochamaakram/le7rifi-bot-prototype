# Security and privacy

Implemented controls are prototype safeguards, not evidence of compliance or a security audit.

Identity: dev bearer token is random/operator supplied and accepted only in development. It maps to a fixed demo identity, never a client-supplied tenant. JWT mode requires pinned issuer/audience/public key and RS256 with required expiry/issued-at/subject/tenant. Real mobile OAuth PKCE, refresh/revocation, trusted tenant membership contract and key rotation are pending.

Data: tenant/user application predicates and forced PostgreSQL row policies protect private conversations, messages, documents, chunks, preferences and usage. Runtime role must be NOSUPERUSER NOBYPASSRLS. The tenant/month quota table holds only aggregate unit counters. Identity settings are transaction-local; default missing settings deny rows. DB administrators are trusted and can still access data. Do not connect runtime as `postgres`.

Input: whole body capped before multipart parsing; upload reads bounded; audio container, size/duration, full decoding and silence checked. Document types, UTF-8/PDF content, page/text/chunk limits checked. Parser bugs/resource exhaustion remain risks: keep dependencies updated and add process/resource isolation before accepting arbitrary public PDFs. There is no arbitrary URL scraping. SaaS remains read-only. No shell interpolation is used with user filenames.

AI: document/profile data is untrusted context separated from system instructions. There are no write tools or hidden service credentials in prompts. References are filtered to retrieved IDs. This reduces attack surface but cannot guarantee that the LLM never follows malicious text. Prompt boundary tests are not a full adversarial evaluation.

Operational: provider timeouts, conservative usage quotas, process-local rate limits, bounded histories/retrieval, safe error codes, metadata-only structured logs and request IDs. One worker only. No payload/authorization logging; uvicorn access logs disabled in Docker. Caddy supplies TLS for public deployment. Exact currency billing limits, distributed rate limiting and request idempotency are pending. Set account-level provider spend limits separately.

Retention: backend raw audio and decoded temporary files deleted after processing; client raw audio deleted after transcription/cancel and playback file deleted/replaced. OS/process crashes can leave temp files; purge temp storage operationally. Provider retention is separate and must be checked with the selected provider. Conversation history pruned lazily on authenticated DB access according to conversation creation age (default 30 days); inactive users are not purged until accessed. Documents/preferences persist until deletion. Preference opt-in is explicit, disabled values are cleared, export and deletion APIs exist. Usage records are not yet purged and are not included in the mobile data export; account deletion/export coverage needs completion.

For Morocco, assess personal-data processing and overseas AI hosting under Law 09-08 with the responsible operator/adviser before a real pilot. CNDP describes notification and foreign-transfer procedures, including the relationship between underlying processing approval and transfer authorization. Do not infer that app consent alone settles these duties. Document controller/processor roles, purposes, recipients/countries, retention, access/rectification/deletion process and processor agreements against the actual deployment. See [CNDP notification procedures](https://www.cndp.ma/procedures-de-notification-process/), [foreign data transfers](https://www.cndp.ma/transfert-de-donnees-a-letranger/), and [Law 09-08](https://www.cndp.ma/wp-content/uploads/2023/11/Loi-09-08-Fr.pdf).

Before a public pilot: validate JWT/tenant mapping against real issuer; run DB RLS tests with the actual runtime role; review file parsing and injection behavior; configure provider controls; test backup restoration; replace debug Android signing; perform device accessibility/network failure checks; complete retention and export/deletion coverage. No real customer data should be used to exercise development mocks.
